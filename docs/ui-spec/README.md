# 奶龙统一门户 · UI 设计规范

**版本** 1.1.1 · **生效日期** 2026-10-30 · **适用** `src/` 全部 SPA 页面与 `animal-island-ui` 组合层

> 这是**本项目自己的** UI 规范。`docs/design-system/` 描述的是上游组件库
> [animal-island-ui](https://github.com/guokaigdg/animal-island-ui)，其中的部分数值已经落后于
> 当前安装的 `animal-island-ui@2.3.0`；两者冲突时，以运行时包和本规范为准。

---

## 0. 这份规范解决什么问题

一套能用的 UI 规范，不是“主色 + 8px 间距 + 统一按钮”的展示页。它要让三类人各自拿到可执行的答案：

| 角色 | 需要回答的问题 | 在本规范中的入口 |
| --- | --- | --- |
| 设计师 | 这个页面该先放什么、用什么层级、什么状态必须画出来 | [01 Foundations](./01-foundations.md) · [05 Layouts](./05-layouts.md) · [04 Patterns](./04-patterns.md) |
| 开发 | 用哪个 token、哪个组件、哪个状态、什么不能写 | [02 Tokens](./02-tokens.md) · [03 Components](./03-components.md) · [04 Patterns](./04-patterns.md) |
| 测试 | 什么算通过、哪些是已知偏差、回归要跑什么 | [06 QA](./06-qa.md) |

三条项目基线贯穿全部六层：

1. **海岛视觉，政务密度**——暖奶油底、大地棕文字、薄荷点缀、pill 控件；但页面要能承载 12 个署、
   百余张表、上千条记录，不能做成营销落地页。
2. **双语同构**——`zh-CN` 与 `zh-TW` 不是翻译插件，而是同一套布局的两种最长文案测试。
3. **异常状态完整、可恢复**——加载、空、失败、离线、无权限、长文案、忙碌、成功、不可逆确认，
   一个都不能少；异常状态属于规范，不是测试阶段再补。

> 规范的价值不是“看起来专业”，而是减少同一个问题被重复设计和重复实现。

## 1. 权威顺序（Source of Truth）

按以下顺序裁决，越靠前越权威：

1. **运行时真实值**：`node_modules/animal-island-ui/dist/index.css` 的 `:root`（48 个
   `--animal-*` 变量）与 `dist/es/components/*/*.module.css`（组件真实样式）。
2. **本规范**：项目级组合、布局、交互、验收规则。
3. **`docs/design-system/`**：上游设计语言与组件像素说明，作为背景参考；数值可能滞后。
4. **页面/设计稿现状**：现状不是规范，只是待收敛的输入。

## 3. 十条硬规则（一页版）

违反任意一条，视为 UI 缺陷，而不是“风格选择”。

1. **只用 token**：颜色、圆角、阴影、字体、动效一律 `var(--animal-*)`；布局常量用
   `--nl-*`（仅限尺寸，不含颜色）。新代码不得出现裸 hex / rgb。
2. **交互元素圆角 ≥ 12px**；按钮/输入框是 50px pill；卡片 20px；Modal 保持 SVG blob；
   Title 保持燕尾飘带。不要用 `border-radius` 把组件改成矩形。
3. **3D 厚阴影只属于 primary / danger-primary 按钮**；Card 无阴影（仅 hover 上浮）；
   Switch 无外阴影；Input 默认无阴影。
4. **焦点必须可见、≥3:1、不被遮挡，且不许用冷蓝**：输入框暖黄、按钮薄荷、Checkbox/Radio 暖黄；
   任何 `outline: none` 都必须有替代焦点样式（必要时加深色内环兜底）；sticky 顶栏/底栏与浮层不能盖住焦点。
5. **状态不能只靠颜色**：错误/成功/警告/未读必须同时有图标、文字或形状差异；状态标签必须带文案。
6. **正文 14px / 1.6，最小 12px**；字重 ≥ 400；标题 600–700（Title 飘带/大数字 800–900）；
   数据数字用 tabular-nums。11px 只允许出现在打印票据/印章等非屏幕 UI 的装饰文字上。
7. **表格必须 `className="table-fit"`**：靠换行压缩进容器，不横向滚动；不传 `size`、
   不写 `ellipsis`；操作列用 `.table-actions`。
8. **弹窗只能显式关闭**：`maskClosable={false}`；异步确认按钮 `loading + disabled`；
   成功后先关窗/重置，再 toast，再 `await load()`；失败保持弹窗。
9. **每个用户可见字符串都走 `t()`**；`zh-CN` 与 `zh-TW` 键结构必须一致；服务端内容用
   `_tw` 双语列，不在前端硬编码翻译。
10. **新页面/改版必须过 [06 QA](./06-qa.md) 的 Definition of Done**；存量偏差按
    §6.5 登记，不因为“一直都这样”而放行新代码。

## 4. 怎么用

### 4.1 设计与交付流程（8 步）

| 步骤 | 做什么 | 本规范入口 |
| --- | --- | --- |
| 1 | **明确业务目标和关键任务**：用户要完成什么、成功长什么样；不要从视觉风格开始 | 任务清单 / 验收条件 |
| 2 | **梳理信息架构和关键流程**：页面关系、入口、返回路径、异常分支 | [04 Patterns](./04-patterns.md) |
| 3 | **低保真验证结构**：先发现流程问题，不急着画高保真 | [05 Layouts](./05-layouts.md) 模板 |
| 4 | **建立 Foundations 和 Tokens**：颜色、字体、间距、圆角先统一 | [01](./01-foundations.md) · [02](./02-tokens.md) |
| 5 | **用组件搭高保真**：减少页面之间的自由发挥，不新造一次性组件 | [03 Components](./03-components.md) |
| 6 | **补齐响应式、异常状态和无障碍**：不同尺寸、键盘、触控、文字放大 | [04](./04-patterns.md) · [05](./05-layouts.md) · [06](./06-qa.md) |
| 7 | **与开发一起完成交付**：交规则、变量、组件、状态和行为，不只交截图 | §4.5 |
| 8 | **上线前 Design QA**：在真实环境核对布局、文案、状态、无障碍和边界 | [06 QA](./06-qa.md) |

> 顺序不要倒：不从视觉风格开始，也不先写“大而全”的文档。先找重复出现的设计决策，
> 再沉淀 Token、组件和 Pattern；本规范是目标状态，不等于要求一次性推倒重来。

### 4.2 设计师

1. 先读 [01 Foundations](./01-foundations.md) 的颜色语义与文字角色，不要先画布局。
2. 用 [05 Layouts](./05-layouts.md) 选页面模板（门户 / 署首页 / 列表工作台 / 详情 / 表单 / 登录）。
3. 每个交互组件至少画 **默认、hover、focus、disabled、loading、error** 六态；
   表单再加 **填写中、成功、只读**；列表再加 **空、失败、无权限、离线、长文案**。
4. focus 状态必须画出来，并标明它不会被 sticky 顶栏/浮层遮住；不要留给浏览器默认样式。
5. 中文最长文案用 `zh-TW` 校对；任何会被截断的标题都不合格。

### 4.3 开发

1. 从 [02 Tokens](./02-tokens.md) 找变量，不抄 hex。
2. 从 [03 Components](./03-components.md) 找组件契约；不要发明 props，以
   `node_modules/animal-island-ui/dist/types` 为准。
3. 从 [04 Patterns](./04-patterns.md) 复制交互顺序（尤其是确认、busy、toast、刷新的顺序）。
4. 提交前跑：`npm run check:i18n && npm run check:ui && npm run lint`。
5. 新增偏差先登记 [06 §6.5](./06-qa.md#65-已知偏差登记)，不要用“库就是这样”绕过。

### 4.4 测试

1. 用 [06 QA](./06-qa.md) 的矩阵：6 档视口、200% 缩放、键盘全程、简繁切换、离线与长文案。
2. 对照 §6.5 判断是“新缺陷”还是“已登记偏差”；新缺陷直接打回。
3. 每个署至少跑一次对应 smoke 脚本（见 §6.2）。
4. 上线前做真实环境 Design QA：真实字体、浏览器、接口数据、权限和慢网，不能只看设计稿。

### 4.5 设计交付包

开发真正需要的是“更少歧义”，不是更多红线标注。每次交付至少包含：

| # | 交付物 | 内容 | 本规范对应 |
| --- | --- | --- | --- |
| 1 | 页面 / 流程 | 入口、返回、关键分支、异常分支 | 04 Patterns |
| 2 | 组件来源 | 用了库的哪个组件/变体；没有则说明为什么新增 | 03 Components |
| 3 | Token / 变量 | 语义名与代码名一致（如 `text-secondary`、`space-4`） | 02 Tokens · `tokens.json` |
| 4 | 组件状态 | hover / focus / disabled / loading / error / empty | 03 状态矩阵 |
| 5 | 响应式规则 | 360 / 640 / 720 / 900 / 1024 / 1440 怎么重排 | 05 Layouts |
| 6 | 交互说明 | 点击后发生什么、busy、成功/失败、焦点去向 | 04 Patterns |
| 7 | 异常状态 | 加载、空、失败、离线、无权限、长文案 | 04 §8 |
| 8 | 资源文件 | 图标名、图片、二维码、字体（不新增第三方字体） | 01 §7 · 02 |
| 9 | 文案规则 | 简繁、最长文案、按钮动词、错误文案 | 01 §9 · 06 |
| 10 | 验收条件 | 可测的对比度/尺寸/键盘/状态清单 | 06 §6.6.2 |

## 5. 范围与非目标

**本版覆盖**

- 门户外壳、12 个署的入口与署内页面、7 个在 SPA 内运行的署（签注 / 入境 / 外交 / 居民 /
  礼宾 / 文书 / 申诉）、管理与审核工作台、登录/注册/首次引导、打印票据。
- `animal-island-ui@2.3.0` 的 30 个在用组件 + `useForm` 与项目自定义组合层。

**本版不做**

- 不重写组件库，不新增第三方 UI/图标库。
- 不做暗色模式：当前库没有暗色 token 集，强行反色会破坏对比度与品牌；见 §6.5 D-12。
- 不把存量页面一次性改成规范值；只要求“新代码合规、被改到的局部顺手收敛”。
- 不替代 `docs/design-system/components/*.md` 的 API 文档；本规范只定义“怎么用、什么算对”。

## 6. 版本与治理

- **版本号**：语义化版本。新增规则/新增层 → minor；修改既有验收线 → major；措辞/示例 → patch。
- **变更流程**：提出 → 在对应层写清“规则、理由、反例、验收方式” → 至少一名前端 + 一名设计/产品
  确认 → 更新 `tokens.json`（如涉及 token）→ 在 [06 QA](./06-qa.md) 登记影响面。
- **偏差登记**：任何暂时不满足规范的存量实现，必须写进 §6.5，包含位置、实测值、影响、收敛计划；
  没有登记的偏差视为缺陷。
- **落地顺序**（不要一次性铺开）：
  1. 先统一颜色、字体、间距、圆角等基础 Token；
  2. 整理使用频率最高的 10–20 个组件；
  3. 补齐组件状态与使用边界；
  4. 把搜索、筛选、表单、弹窗等重复流程整理成 Pattern；
  5. 最后做复杂页面模板与跨署规范。
  本项目已有第 1–3 步的基础（token、组件、状态），当前重点是把第 4–6 层落到页面并收敛存量偏差。
- **本文档的来源**：项目笔记中的 UI 设计文章（正文 + 续篇）给出了六层框架、语义色、文字角色、
  触控/键盘与 WCAG 2.2 基线、异常状态、设计流程、交付包与 FAQ。两篇笔记合并后按同一套六层框架
  落地到本仓库的真实组件、token、页面与验收脚本；续篇补上了此前被截断的键盘焦点与异常状态部分。

## 8. FAQ

**一定要用 8px 网格吗？**
不一定。4px、8px 或其他尺度都可以，关键是规则足够少、可复用、能覆盖目标设备和组件尺寸。
本项目选 4px，是为了和 `--animal-spacing-*` 对齐。

**按钮最小尺寸是多少？**
WCAG 2.2 AA 的指针目标最低要求是 24×24 CSS px（存在间距等例外），但 24px 不是推荐按钮高度。
本项目：密集后台 32×32，主操作/移动端 ≥44×44；视觉图标可以更小，可点区域不能小。

**iOS 按钮必须 44×44pt 吗？**
Apple HIG 把 44×44pt 列为默认控件尺寸，同时列出 28×28pt 的最低控件尺寸，并强调控件间距。
不要把所有按钮视觉都做成 44×44；要保证可点区域和间距足够。

**UI 和 UX 有什么区别？**
UI 负责看得见、可操作的界面表达：视觉层级、组件、状态、反馈。UX 还包括用户研究、信息架构、
服务流程和任务完成质量。本规范只管 UI 表达与设计交付，不替代业务流程/用户研究文档。

**小团队需要做完整 Design System 吗？**
通常不需要从“大而全”开始。先统一 Token，再整理 10–20 个高频组件、状态和 Pattern，
产品结构稳定后再扩展页面模板。见 §6 的落地顺序。

**无障碍是不是只有政府或大型产品才需要？**
不是。对比度、焦点、触控尺寸、文字放大、错误提示都会改善普通用户的使用体验；
是否需要达到某个法律/行业合规级别，要按产品所在地区和业务场景单独判断。

**设计完成后还需要 Design QA 吗？**
需要。静态设计稿覆盖不了真实字体渲染、浏览器差异、接口数据、长文案、加载状态和响应式变化。
Design QA 的作用是在真实产品里确认“规则是否真的被实现”。

**为什么不做暗色模式？**
当前 `animal-island-ui@2.3.0` 没有暗色 token 集，局部反色会破坏对比度和品牌。暗色模式作为独立版本
立项，必须成对定义 token、重新跑对比度，不能简单把背景翻黑。
